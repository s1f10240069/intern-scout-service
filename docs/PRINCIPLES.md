# 開発の判断と工夫

最終更新: 2026-09-19

この文書は、何を優先して実装したか、AIをどのように開発へ取り込んだか、設計・実装・UIでどのような判断をしたかをまとめたものです。要件の正本は [REQUIREMENTS.md](REQUIREMENTS.md)、画面とAPIの詳細は [SCREEN_FLOW.md](SCREEN_FLOW.md) を参照してください。

## 1. 優先順位の付け方

優先度は「ユーザー価値」「前提となる依存関係」「短いサイクルで確認できるか」の3点で判断しました。完成度を広げるより、学生と企業がそれぞれ目的を達成できる最小の一連の体験を先に完成させる方針です。

| 優先度 | 実装範囲 | この順番にした理由 |
| --- | --- | --- |
| 1 | 学生・企業の登録、ログイン、認証 | 誰がサービスを使っているかを識別できなければ、役割ごとの体験やデータ保護を成立させられないため。 |
| 2 | 企業の学生閲覧、メッセージ開始・返信 | スカウトサービスの中心である「企業が学生へアプローチし、学生が応答する」価値を最短で検証するため。 |
| 3 | 求人の掲載・閲覧 | 企業と学生の接点を増やすが、認証と役割別の画面・データ取得が先に必要だったため。 |
| 4 | 検索・絞り込み、お気に入り、大学サジェスト | 利便性は高い一方、基本導線が動くことを確認してから効果を判断できるため。 |

特にメッセージ機能では、学生を表す名称・パスを先に統一しました。基盤を整理せずに機能を載せると、関連する画面・API・テストの修正範囲が広がるためです。変更は小さく分け、動作確認できる状態を保ちながら進めました。

## 2. AIを用いたコーディングでの工夫

AIは実装を速くするための補助として使い、要件の解釈と最終判断は人が担う運用にしました。

- **前提を文書で固定する**: 要件、画面遷移、現状、次の作業を `docs/` に分け、AIに渡す文脈が毎回ぶれないようにした。
- **変更を小さく依頼する**: 画面、API、データモデルを一度に大きく変えず、表示・取得・結合の単位に分けた。差分が読みやすくなり、意図しない変更を見つけやすい。
- **実装後に根拠を確認する**: AIが出したコードも、認可の境界、入力値、既存画面への影響を人が確認し、結合テスト・lint・ビルドで検証する。
- **作業再開を容易にする**: [AI_HANDOFF.md](AI_HANDOFF.md) に実装済みの範囲、注意点、次の候補を残し、会話や作業セッションが変わっても同じ前提から再開できるようにした。

AIの提案をそのまま採用しないことも重要です。とくに認証・認可、データ削除、既存仕様の変更は、コードとテストで裏付けを取ってから反映します。

## 3. 設計・コード実装での工夫

### 役割ごとのデータ境界

学生と企業で利用できるAPIを分け、企業の操作は `current_company` にひもづくデータだけを取得・更新する設計にしています。たとえば求人の更新・削除は、URLのIDだけを信頼せず、ログイン中の企業が所有する求人として検索します。別企業のデータにはアクセスできません。

メッセージは `Conversation` を企業と学生の組み合わせで一意にし、同じ組み合わせで会話が重複しないよう、モデルのバリデーションとデータベースの一意制約の両方で守っています。送信者種別とメッセージ本文もサーバー側で正規化・検証します。

### フロントエンドの共通化

- `apiFetch()` にJSON送信、Bearerトークン、HTTPエラー処理を集約し、ページごとの通信実装のばらつきを抑えた。
- `useAuthenticatedResource()` で、トークン取得、未認証時の遷移、401/403時のトークン削除と遷移を共通化した。
- `AppShell`、`Button`、`Input`、`Card`、`Field` を共通コンポーネントにし、画面間の構造と見た目をそろえた。

このように、共通になる判断は一か所へ寄せ、画面コンポーネントには画面固有の表示と操作を残すようにしています。

### 検証を実装に組み込む

Railsの結合テストでは、会話の重複防止、他者の会話や求人へのアクセス拒否、空文字・過大な入力の拒否を確認しています。フロントエンドはPrettier、ESLint、ビルドをGitHub Actionsで実行し、表示変更が品質チェックを通る状態を保ちます。

## 4. UIでの工夫

- **役割を迷わせない**: ログイン・登録画面で学生／企業を選択し、選択後はそれぞれの目的に合う画面へ遷移する。
- **共通の操作感**: ヘッダー、余白、カード、フォーム、ボタンのルールを共通化し、画面が変わっても操作の学習コストを下げる。
- **状態を伝える**: 読み込み中、通信エラー、送信中、空の状態を明示し、操作しても反応がないように見える場面を減らす。
- **画面幅に対応する**: 認証画面、一覧、フォーム、メッセージ送信欄は小さい画面で1列表示や全幅ボタンへ切り替える。
- **メッセージを読みやすくする**: 自分と相手のメッセージを配置と色で区別し、長文は改行を保ったまま表示する。

## 5. 次に判断すること

基本導線を目視で確認したうえで、検索・絞り込み、お気に入り、大学サジェストの順に必要性を判断します。追加機能では毎回、「どちらの利用者の、どの行動を良くするか」「既存の認可・データ境界を保てるか」「最小の単位で検証できるか」を確認します。

## 更新ルール

優先順位や設計判断を変えたときは、この文書を更新します。画面やAPIの具体的な変更は `SCREEN_FLOW.md`、要件そのものの変更は `REQUIREMENTS.md` に反映します。
