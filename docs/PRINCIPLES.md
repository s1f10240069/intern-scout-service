# 設計方針・開発アプローチ

最終更新: 2026-09-15

機能を検討・実装する際に立ち返る**開発の原則**をまとめた文書。元は `docs/REQUIREMENTS.md` の「設計方針」に記載していた内容を独立させた。

- 要件の正本: `docs/REQUIREMENTS.md`
- 画面遷移・実装差分: `docs/SCREEN_FLOW.md`
- 進捗・設計経緯: `docs/PROGRESS.md`
- 作業再開用の要約: `docs/AI_HANDOFF.md`

## 原則1: 「誰が何を達成したいか」を軸に機能を検討する

機能を考えるときは、まずユーザーとその目的を明確にする。実装のしやすさや技術的な興味で機能を選ばない。

- **企業**: 良い学生を効率的に見つけたい・アプローチしたい
- **学生**: 自分に合う企業を見つけたい・魅力を知りたい

新しい機能を検討する際は「これは企業（または学生）のどの目的に寄与するか」を毎回確認する。

## 原則2: 複雑な要求をシンプルな単位に分解して実装する

大きな機能を一度に作らず、小さな単位に分解して段階的に実装する。

- 例: **表示 → 取得ロジック → 結合** の順で進める
- 1回の変更を小さく保ち、動く状態でこまめに確認する

## 原則3: 未完成でも構わないので、優先度をつけて実装範囲を決める

完璧を目指すより、**動くプロトタイプ**を優先する。優先度をつけて、できる範囲まで実装する。

現在の優先順位（詳細）:

### 優先度1: 学生が登録できる（実装済み）

- 登録 / ログイン / マイページ（API・画面）
- 認証（トークン発行・`localStorage` 保存）

### 優先度2-A: メッセージ実装前に行う最小限の基盤整理（完了）

メッセージの関連付け・画面リンク・テストを旧名称で作ると後の修正範囲が広がるため、次の2点だけは先に行う。

- ドメイン識別子の呼称リネーム: `Intern` → `Student`、`interns` → `students`、`internApiToken` → `studentApiToken`
- 企業側学生一覧のパス改称: `/companies/dashboard` → `/company/students`

既存画面やAPIを一度に削除せず、新旧ルートの一時併存・リダイレクト・トークンキーのフォールバックを使って段階的に移行する。詳細は `docs/SCREEN_FLOW.md` の「安全な移行手順」を参照。

### 優先度2-B: 企業と学生のメッセージ（未着手）

1. `Conversation` / `Message` モデル・マイグレーション
2. 認可を含む API
3. 企業側: 学生詳細＋会話（送信・返信）
4. 学生側: 会話一覧・スレッド（閲覧・返信）

### 優先度3: 企業が募集（求人）を掲載できる（未着手・設計済み）

1. `JobPosting` モデル・`job_postings` テーブルのマイグレーション
2. 求人 API（一覧・詳細・作成・更新・削除）
3. 企業側: 求人管理（投稿・一覧・編集）
4. 学生側: 企業一覧・企業ホームページ・求人詳細（閲覧）

### 優先度4以降: 追加機能（将来設計）

- 検索・絞り込み（学生検索 / 求人検索）
- お気に入り／ブックマーク（3方向: 企業→学生 / 学生→企業 / 学生→求人）
- 大学サジェスト（まずは静的リスト）

統合ログイン / 登録（`/login`・`/register` でアカウント種別を選択）は、メッセージのデータモデルに影響せず後から変更しても手戻りが限定的なため、優先度2-Bの後に行う。

具体的な差分と優先順位は `docs/SCREEN_FLOW.md` を参照。
